# SenseLex Atlas, browser edition

This folder holds a self-contained web page, `index.html`, that is a working tool for building, collecting, and analysing multisensory lexical norms. It needs no installation, no build step, no server-side code, and no account or login. Everything runs in the browser, and the data you collect is saved on your own device. It loads a companion file, `words.js`, which carries an English word bank with frequency and concreteness.

## What you can do with it

You can draw a study set from a word bank under controlled conditions, choosing a language, how many words you want, and the frequency range, and for English the concreteness range as well, so a list is a sample you have designed rather than a handful of fixed words. You can then run a sensorimotor rating session, presenting each word and recording its strength on the eleven perceptual and action channels of the Lancaster protocol, or a free-naming session that records the name a participant gives for each item. The prompt can be read aloud through the browser's speech synthesis, which helps with participants who do not read, including children and people with reading difficulty. As data accumulate, the Explore tab computes the norms live: the dominant modality, the maximum perceptual strength, the modality-exclusivity score, a rater-spread reliability cue, and the codability of any naming responses. You can sort, filter by concreteness or frequency, and download the norms as CSV, alongside a trial-level long-format CSV (one row per participant, word and dimension) for archiving and reanalysis.

You manage everything under the Build and manage tab. The word list is editable by hand or by pasting a list, you can add languages with their script and direction, and the whole dataset exports to JSON for backup or transfer and imports back with a merge that does not duplicate records.

## The word banks

`words.js` holds one word bank per language. Every bank carries a Zipf word-frequency value for each word, so the study builder can sample across the frequency range, and the English bank additionally carries a mean concreteness rating, so for English the builder can also constrain concreteness. The banks are a derived feature subset of published resources, and they give the languages roughly equal coverage rather than leaving most of them with only a few words.

Word frequency, for every language, comes from the wordfreq package (Speer, 2022), https://doi.org/10.5281/zenodo.7199437, which provides Zipf frequencies built from a blend of corpora. Mean concreteness, for English only, comes from Brysbaert, Warriner and Kuperman (2014), Behavior Research Methods 46(3), 904 to 911, https://doi.org/10.3758/s13428-013-0403-5. Concreteness ratings of this kind are not available in a comparable form for the other languages, which is part of what the tool exists to address. The banks are distributed with attribution rather than relicensed, and anyone using the words should cite the sources.

A few languages that the frequency corpus does not cover, such as Swahili, Yoruba, Basque and Thai in the current build, keep a small set of hand-checked core words instead of a bank. Arabic, Hebrew, Tamil, Vietnamese, Turkish and Japanese keep the same hand-checked core words for a different reason: wordfreq does cover them, but a repeated, multi-round adversarial audit found their derived banks kept a large share of proper nouns, foreign intrusions, bound morphemes or unresolved inflected forms even after every filter in the pipeline ran, including a per-language NLP pass. Measured junk rates ran from about 14% (Japanese) to about 60% (Arabic), well above the roughly 2 to 12% seen for every other curated language, so these six are left on the small hand-checked list rather than shipped with a noisy bank. See `../data/README.md` for the detail and the exact figures.

`words.js` is generated by `../data/build_wordbanks.py`, which also curates each bank down to genuine content words rather than shipping raw frequency lists; see `../data/README.md` for the full pipeline and its dependencies. The raw source files are not committed.

## Study links and recruitment platforms

A study link preconfigures a session through URL parameters, so a recruitment
platform can send participants straight into a task with nothing to set up on
screen:

- `?lang=spa&task=rating` preselects the language and the task.
- `&cc=CODE` holds a Prolific completion code. When every item is complete, the
  page shows a Return to Prolific link that registers the submission.
- `&atlas=https://your-atlas.example&token=TOKEN` submits ratings to a hosted
  Atlas as they are saved. Submission is idempotent (each record's id is the
  client id, so a retried upload cannot double-count), it retries on failure and
  when the connection returns, and the page states on screen that submission is
  happening and to where. Naming responses stay local, because the Atlas stores
  coded responses and coding is an analyst's judgement. A rating edited after
  successful submission stays local.

Prolific's own `PROLIFIC_PID`, `STUDY_ID` and `SESSION_ID` parameters are read
automatically: the participant code locks to the Prolific id and all three are
stored with each record. The same mechanics serve any panel that can append URL
parameters to a study address.

## Run the study elsewhere (jsPsych)

Under Build & manage, "Run the study elsewhere" exports the items of one
language as a ready-to-run jsPsych 8 experiment: a single HTML file that
presents the same rating instrument, passes Prolific parameters through at run
time, and saves its data both as a jsPsych CSV and as a SenseLex dataset file
that imports straight back here or into the full Atlas. A standalone jsPsych
plugin for embedding the trial in your own timelines lives in
`../integrations/jspsych/`.

## Viewing and hosting it

Open `index.html` in any modern browser. `words.js` loads alongside it, so keep the two files together. To serve it over a local address instead, run a static server from this folder, for example `python -m http.server 4173`, then open `http://localhost:4173/`. Because these are static files, any static host will serve them with no configuration. The quickest route is a drag-and-drop deploy onto Netlify Drop or Cloudflare Pages, which returns a public URL in under a minute, or, if the project is pushed to GitHub, GitHub Pages will serve the folder directly.

## What the data never does

The data you collect stays in this browser's local storage on this device, with
one exception you control: a study link that names an Atlas address submits
ratings there as they are saved, and the page says so on screen. There is
otherwise no upload, no account, and no tracking. Export the data to move it
elsewhere.

## Relation to the full Atlas

The full Atlas, in the parent `software` folder, adds what a single page cannot: shared online collection by many contributors with authentication, the offline-first field client with idempotent synchronisation, a server database, and the FAIR export endpoints. The browser edition and the full service share the same norm mathematics, and a dataset exported here can be carried into the service.
